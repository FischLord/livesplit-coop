# Protocol v3

Transport: UTF-8 JSON text messages over WSS at `/coop/<room>`, where `<room>` is 1–64 letters, digits, `_` or `-`. The component takes the server URL `wss://host/coop` and the room name separately and appends the room itself, so a relay (for example a Cloudflare Worker) can route to the room before the upgrade. Maximum message size 256 KiB; no compression. Plain WS is development-only on loopback. Credentials never appear in the URL. Browser Origin requests are rejected; this endpoint is for native clients.

The first message, within five seconds, is `{ "type":"hello", "v":3, "role":"host|viewer", "key":"..." }`. The key never appears in the URL. The relay responds with `ready`. A hello with another version is closed with 1008 and a reason asking to update the component; the bare `/coop` path stays open for that purpose, so v1/v2 clients (0.1.0-beta.1/beta.2) are told to update instead of failing the handshake. A v3 hello without a room in the path is closed with 1008. A room the relay does not know, or that has expired, is closed with **4004** `Room expired or unknown`; the component stops reconnecting and asks the user to check the room or create a new one.

Rooms are either preconfigured (`rooms.json`, never expire) or, when the operator enables it (`ROOM_CREATION=1`), created with `POST /rooms` without a body. The answer is `201 { "roomId", "hostKey", "viewerKey", "idleExpiryDays" }`: a random 22-character room ID and two independent 256-bit keys. Requests carrying an `Origin` header are refused, so websites cannot create rooms. Creation is limited globally per hour (429 with `Retry-After`) and by a total room count (503). Created rooms are kept in memory only and are removed after seven days without any connection; a relay restart discards them. The Cloudflare relay (`relay-cloudflare/`) stores them in its Durable Object instead and survives restarts; its creation limits are per client IP and per day.

An invite is one line of text, `lscoop:1:<server>/<room>#<viewerKey>`, for example `lscoop:1:wss://relay.example/coop/AbC…#key`. It is never sent to the relay; the component splits it into server URL, room and viewer key and applies the same validation as for manual input. It never contains the host key. Invalid authentication/messages close with 1008. The component stops reconnecting after invalid authentication, incompatible protocol or other permanent policy violations; room capacity and hello-deadline rejections are temporary and are retried.

A room holds one host and up to eleven viewers; viewers can never take the host's slot. A new connection that authenticates with the host key replaces the current host connection, which is closed with code 4001. The component stops reconnecting after 4001, so two PCs configured as host do not keep replacing each other; a host whose previous socket died silently can publish again at once.

Unauthenticated sockets do not count against the relay's member limit. At most 16 wait for their hello at a time; when another arrives, the oldest waiting socket is dropped. Client addresses are deliberately not used by the reference relay, since rootless port forwarding and reverse proxies can hide them. The Cloudflare relay is the exception: it reads `CF-Connecting-IP` (bucketed per /64 for IPv6) solely for the per-room failed-login lockout described under Lobbies; addresses are not logged.

The host publishes a complete `snapshot` after connecting and whenever anything other than the running clock changes. Otherwise it sends a `tick` of about 100 bytes, `{ "type":"tick", "v":2, "seq":n, "realTicks":n|null, "gameTicks":n|null, "gamePaused":bool }`, at four per second. The relay only accepts a tick after a snapshot from the same connection, merges it into its cached snapshot and validates the result. See `component/Snapshot.cs` and `relay/src/protocol.mjs` for the schema. Times are nullable integer .NET ticks (100 ns), bounded to seven days, well inside JavaScript's exact integer range. Missing Game Time remains `null`. Snapshots include every segment, completed times, PBs, best segments and named comparisons. All array indexes are validated. Ended snapshots must exactly match the last split's values, including after a tick.

`seq` must increase within a host connection, across snapshots and ticks. The relay ignores older/duplicate sequence values. Reconnecting creates a new connection sequence domain. `runId` identifies the in-memory run; `attemptId` changes on start/reset. No receiver-side command replay is necessary: a newer snapshot replaces the displayed state.

Viewers receive `{ "type":"state", "live":true|false, "ageMs":0, "snapshot":{...} }` and forwarded ticks `{ "type":"tick", "seq", "realTicks", "gameTicks", "gamePaused" }`. The relay serialises each broadcast once for all viewers. A new viewer immediately receives the cached, tick-merged snapshot, if any. Cached snapshots include their server residence age; disconnected/old snapshots are not considered live. `{ "type":"host", "online":false }` announces loss of the publisher. A host reconnect must publish afresh before existing viewers resume. The Cloudflare relay additionally sends the host `{ "type":"peers", "viewers":n }` after its hello and whenever a viewer joins or leaves; older clients ignore the unknown type.

The component interpolates running time using a local monotonic stopwatch since receipt, plus the cached packet's age. It does not claim network-clock synchronization or subtract guessed latency. When stale, interpolation is bounded to 1.5 seconds and frozen. Paused/final times and all completed split values are never interpolated. Ticks update the viewer's clock without rebuilding its run. Missing heartbeats and slow clients are disconnected; application `ping` gets `pong` and WebSocket ping/pong checks transport liveness. Clients ping every five seconds and reconnect when nothing arrives for 15 seconds (10 seconds before `ready`).

The relay retains only the latest snapshot per configured room in memory, even after a host disconnect, until another snapshot replaces it or the service restarts. It does not write run data to disk, execute commands, accept arbitrary filenames or retrieve URLs supplied by clients.

## Lobbies (Cloudflare relay)

A lobby is a room with a chosen name. The WebSocket protocol is unchanged (v3); only creation differs.

- Name: 3–32 characters `[a-z0-9_-]`; the relay trims and lowercases. Room ID: `lobby_<name>`.
- Viewer key: derived by the client, `base64url(PBKDF2-HMAC-SHA256(password, "livesplit-coop-lobby:v1:" + name, 100000, 32 bytes))`, no padding. An empty password is allowed. The password never leaves the client.
- `POST /lobbies` with `{"name","viewerKey","public","locked"}` (max. 1 KiB, no `Origin` header) → `201 {"roomId","hostKey","idleExpiryDays"}`; `409` name taken; `400` invalid; `429`/`503` as for `/rooms`.
- `GET /lobbies` → `200 {"lobbies":[{"name","locked","hostOnline","viewers","game","category","label","updated"}]}`: public lobbies active within 24 h, hosts online first, at most 100. `label` is the host snapshot's optional `profileLabel` (published only if it is plain text of at most 60 characters). `GET /lobbies` is a public read without `Origin` restriction. Entries are refreshed at most every 10 s per lobby, so changes can show up with a delay of up to roughly 15 s.
- Ten failed logins within 60 s from one address (IPv6: one /64) lock that address out of that room for the rest of the window (`1008 Too many attempts`), regardless of the key.
- Lobbies expire like rooms (7 days unused); the name becomes free again.
- Relays without lobby support answer `404` to `/lobbies`; clients fall back to invitations.
